4) CAUSE RACINE documentée (honnêteté : bug réel trouvé et corrigé par les tests)
   Premier état du code : poignée refusée, serveur "no suitable signature algorithm".
   Les deux callbacks PSK s'exécutaient pourtant (traces DEVLINK_TLS_TRACE=1).
   Diagnostic contre les sources openssl-3.0.20 (ssl/statem/extensions_srvr.c
   tls_parse_ctos_psk, ssl/t1_lib.c tls_choose_sigalg) : le serveur sélectionne sa
   suite AVANT reprise ; par défaut TLS_AES_256_GCM_SHA384, dont le digest rend la
   session PSK SHA-256 incompatible => session jetée => repli certificats => échec.
   Correctif : suite unique épinglée des DEUX côtés (SSL_CTX_set_ciphersuites
   "TLS_AES_128_GCM_SHA256") + callback client honorant le digest demandé (refus
   si != SHA256). Après correctif : poignée mutuelle vérifiée.
   Pièges d'ABI vérifiés contre la table d'export (nm -D) :
     SSL_CTX_set_min/max_proto_version = MACROS => SSL_CTX_ctrl lié (ctrl 123/124,
       constantes lues dans include/openssl/ssl.h.in tag openssl-3.0.20)
     SSL_get_cipher_name = MACRO => SSL_get_current_cipher + SSL_CIPHER_get_name
     SSL_SESSION_set_master_key => nom réel SSL_SESSION_set1_master_key
