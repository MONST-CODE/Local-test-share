2. Anomalie `renamed-ico` reproduite, cause racine et correction
-----------------------------------------------------------------
L'investigation a reproduit un vrai défaut du selftest. L'appel historique était :

  probe --ico <fake.ico>

Le probe n'accepte le mode ICO qu'avec cinq arguments (`--ico`, chemin,
`--expect-entries`, nombre). Avec l'appel incomplet il tombait dans le chemin de
sonde générique Linux, retournait 0, et le journal affichait à la fois
« FAIL test=renamed-ico expected=0 actual=0 » et une suite globale éventuellement
verte. Ce n'était donc pas un faux positif du parseur ICO : le cas négatif ne
l'atteignait tout simplement pas.

Corrections conservées dans `build.sh` et `tests/build/toolchain_probe.cpp` :
- l'appel négatif indique maintenant `--expect-entries 7` ;
- le code de retour attendu est explicitement 1 et la sortie exige
  `ICO validation failed` ;
- mêmes contrats explicites (exit 1 + diagnostic) pour les fixtures PE malformée,
  manifeste absent et version incorrecte ;
- le test de propagation de l'exit 23 n'utilise plus `expect` avec un résultat
  volontairement inattendu : il vérifie directement le code et le texte, pour que
  le journal ne présente plus un échec attendu comme un test échoué.

Résultat : le log final contient `PASS renamed-ico: exit=1`, les trois contrôles
négatifs PE sont PASS (exit 1 attendu), et aucun `FAIL test=`. Le selftest a fini
avec `SELFTEST_EXIT=0`. Les lignes `FAILURE: publish_release` du journal sont
intentionnelles : elles vérifient le refus d'écraser une archive d'empreinte
différente et le rejet d'une archive illisible ; les assertions correspondantes
`PASS release-publish-proof` et `PASS clean-preserves-releases-proof` passent.

4. Partage navigateur et système Windows
----------------------------------------
Le backend WebView2 réel reste indisponible/non implémenté. Son code échoue fermé ;
la présence du runtime n'est pas assimilée à une capacité de partage. L'interface
refuse l'ouverture d'une session hôte avant création de secrets ou sockets si
aucun moteur réel opérationnel n'existe. `ManagedBrowserBackend` est uniquement
une fixture synthétique. Aucune qualification de partage navigateur réel n'a été
exécutée.

Aucune exécution Windows, build UCRT64, capture WebView2 ni bascule PerMonitorV2
sur écrans physiques n'a eu lieu. Dans cet environnement `DISPLAY` est absent,
Xvfb et les en-têtes X11 aussi. Ces points demeurent BLOCKED / non vérifiés et ne
sont pas transformés en PASS par les preuves Linux headless.

5. DPI — portée de la preuve
----------------------------
La sonde utilise la vraie typographie DevLink, ImGui 1.93, SDL3 et le renderer
logiciel, mesure les pixels réellement dessinés et écrit des captures 960x480.
Les facteurs 100/125/150/200 % sont injectés comme paramètres typographiques ;
SDL dummy rapporte `SDL_window_scale=1.00` aux quatre runs. Cela prouve le rendu
logiciel aux tailles demandées, pas une transition de DPI physique du système.
Les captures PNG sont `docs/reports/evidence/dpi-captures/dpi-{100,125,150,200}.png` ;
la procédure, les métriques et cette limite sont détaillées dans
`docs/reports/evidence/dpi-multi-scale.txt`.
